# Control Pipeline Rule — 2/2 (Articles 9-15)
Target location: `.agents/rules/`. Continuation of `control-pipeline-rule-01.md` (Articles 0-8), same binding force — the reason for the split is explained there.

## Binding Rules (continued)

9. **Default State Rule**: In the face of ambiguity or missing evidence, the default decision of both the Auditor and the Judge leans negative (REJECTED / INCOMPLETE). Phrases like "there's probably no issue" or "it most likely passed" do not count as valid justification; the burden of proof always sits with the Worker Agent.

10. **Role Non-Mixing**: A single output block cannot represent more than one role at the same time (e.g. both plan and approval in the same message, or both audit and correction in the same message). Role transitions are triggered explicitly by a user request or a workflow step; one role cannot "hand itself off" to the next role on its own.

11. **Perspective Independence**: The Auditor and the Judge may not accept the Worker Agent's justification in the plan/deliverable ("this works this way because...") as their starting point. Both start from scratch with their own independent checklist; neither may carry the Worker Agent's terminology or "logically correct" framing over as justification for their own decision. If the Worker Agent, the Auditor, and the Judge are all run within a single session sharing the same context window, using different role prompts, this constitutes an independence constraint and must be explicitly noted in the Pre-Check Declaration with the following added line: `INDEPENDENCE NOTE: Operating as a different role within the same session — the role separation is procedural only, not context-level.` For high-risk tasks — data schema, security, authentication, payment/financial logic — the Auditor and the Judge should, where possible, be run with contextual isolation from the Worker Agent's plan (given only the rule files and the deliverable); if this is not possible, the user is explicitly informed.

    **How contextual isolation is achieved (concrete example)**: Antigravity's built-in `self` sub-agent, invoked via the `invoke_subagent` tool, uses the same toolset as the main agent but does not inherit prior conversation history — it starts with a clean context. For high-risk tasks, the Auditor/Judge step is invoked via `invoke_subagent(self)` with only the rule files and the deliverable passed in — not the Worker Agent's plan/justification text; this concretely satisfies Article 11, and since it does not pollute the main agent's context with intermediate steps, it does not increase overall token consumption but rather reduces it, per Antigravity's own documentation. If this is not possible, it is simulated within the current session by changing the role prompt and flagged in the INDEPENDENCE NOTE.

12. **Scaled Chain (Light Mode)**: If **all** of the following four conditions are met, the Plan Gate and the Code Gate may be merged sequentially into a single Auditor pass (the roles and decision steps are still produced separately — only the return to the user between them is skipped):
    - The change is confined to a single file and involves fewer than 15 lines of net change.
    - The change is reversible (**not** a migration, data deletion, permission/access change, or external API contract change).
    - A test already covers the change, or one is being added with the deliverable.
    - The change does not alter the signature of a function/API called by another module.

    If **even one** of these conditions is doubtful, the full two-gate process applies per Article 9 (Default State Rule) — light mode is the exception, not the default, and the burden of proof still sits with the Worker Agent. When light mode is used, this must be explicitly flagged in the Auditor's decision as `LIGHT CHAIN APPLIED: (brief justification for each of the 4 conditions)` and logged with this justification. Light mode never skips the Approval Gate (Article 2) or the Judge stage in any way — it only reduces how often the Plan/Code split returns to the user.

    **Documentation/Comment Exception**: If the change consists only of comment lines, documentation (`.md`, README), or formatting/whitespace, and changes no executable line, the fourth condition above ("a test covers/is added for the change") is replaced by this condition: "the Worker Agent has shown, line by line, that the diff consists only of comment/doc/whitespace lines." The other three conditions (single file, reversible, no external signature change) still apply as-is. If even a single executable/logic line appears in the diff, this exception no longer applies and the full process is used — doubt again favors rejection (Article 9).

13. **Activity Summary**: Whenever the user requests it, or once every 10 completed tasks, the Judge scans all records under `.agents/logs/` and produces a summary with the following headings: total task count, Auditor rejection rate, most common rejection-reason categories (evidence gap / loophole / implicit assumption / pattern deviation / rule conflict), recurring violation patterns, light-chain usage rate, and the number of tasks in which light mode later caused problems (if any). This summary reflects the system's concrete historical performance; phrases like "it's probably been helpful" do not substitute for this summary — the summary is derived only from the records, never from estimation.

14. **Deadlock Protocol**: If, within the same task and on the same concrete point, the Auditor or the Judge issues REJECTED/INCOMPLETE for the **third consecutive time** — i.e. the Worker Agent has fixed and resubmitted the same item three times and been turned back for the same reason each time — the chain does not automatically repeat a fourth time. Instead, the role in question presents the user with an explicit `DEADLOCK NOTICE`: the Worker Agent's latest proposal and the Auditor's/Judge's latest justification are shown side by side, and the user is asked to choose one of the following — (a) continue by clarifying the rule/plan, (b) continue by narrowing scope (flagged as a new `ASSUMPTION:`), or (c) hold the task as-is. The counter does not reset without user intervention, and a fourth automatic round is not self-initiated. This article does not weaken the Approval Gate (Article 2) — it only makes the infinite loop visible to the user.

15. **Rule Conflict Notice**: If two or more of the `.md` files scanned under Article 0 contain conflicting requirements on the same subject (e.g. two different decision files define different constraints for the same field), no role may silently resolve this conflict on its own and favor one file over the other — this differs from the case where the `judge` skill's Reference Hierarchy resolves a plan-vs-rule conflict, because there a clear priority order exists; here two rule sources directly conflict and priority is undefined. The conflict is added to the Pre-Check Declaration as a `RULE CONFLICT: (conflicting files + subject)` line, and the task in question is treated as REJECTED/INCOMPLETE under Article 9 (Default State Rule) until the user explicitly resolves the conflict.

16. **Empirical Verification Mandate (Ampirik Çalışma Zamanı Doğrulama Kuralı)**: No role (Worker Agent, Auditor, or Judge) may ever claim or declare to the user that a bug is fixed, a configuration is complete, or a feature is working ("düzelttim", "oldu", "tamamlandı") without FIRST executing real runtime verification commands (e.g. running live API/database integration tests, real network/query validation scripts, or build verification) and demonstrating concrete, empirical output evidence in the response. Simply modifying a file or pushing code to Git does NOT equal completing or resolving a task. In the absence of direct empirical runtime test evidence, the task status MUST remain unverified and cannot be reported as resolved.

## Note
This rule (both parts together) governs not *how* the `isci-ajan` (Worker Agent), `denetci` (Auditor), and `yargic` (Judge) skills work, but *when, in what order, and with what strictness* they operate. The skills' own content defines the detailed behavior of each role; if they conflict with these files, these files win.
